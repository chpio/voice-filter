# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`voice-filter` is going to be a live voice filter for Linux: a single Rust process acting as a PipeWire node that reads the microphone, runs it through a chain of stages (echo cancellation, DeepFilterNet3 denoising, classic DSP voice enhancement; Hush for suppressing other voices is postponed after a test, see the concept) and exposes the result as the virtual microphone "Voice Filter". The design, model choice, latency budget and roadmap are in `docs/concept.md` (started as a German document, now authoritative here). So far there's the vendored DeepFilterNet3 inference (`crates/deep-filter-rt`), the stage chain (DeepFilterNet3, high-pass, EQ, de-esser, AGC, compressor, limiter), the offline mode and a first live mode. Building needs the PipeWire development files, clang (bindgen), GTK 4 and libadwaita (the latter two only for the default feature `gui`).

## Commands

```bash
cargo build
cargo clippy --workspace --all-targets
cargo test --workspace
cargo test --release -p deep-filter-rt   # the model runs about 10x faster than in debug builds
cargo run --release -- process in.wav out.wav   # offline mode, prints latency and time per stage
cargo run --release -- run [--input <name>]     # live: the virtual microphone "Voice Filter", until Ctrl+C
cargo run --release -- inputs                   # the microphones for --input
cargo run -- ui                                 # the GNOME app, needs `run` for its controls
cargo fmt --all            # 4 spaces (rustfmt default, matches .editorconfig)
cargo deny check           # licenses, advisories, sources (deny.toml)
cargo machete              # unused dependencies
typos                      # spell check
```

Tests live in `tests/` of each crate (integration tests against the library, no inline `#[cfg(test)]` modules).

## Architecture

- **Workspace**: the root package `voice-filter` and `crates/deep-filter-rt`; edition, MSRV and license are shared in `[workspace.package]` of the root `Cargo.toml`.
- **Crate layout** of voice-filter: all modules live in the library (`lib.rs`) so tests under `tests/` can use them; the binary (`main.rs`, clap, subcommands `run`, `inputs`, `process`, `ui`) only wires them up. One binary, but the daemon (`run`) and the app (`ui`) are separate processes, so closing or crashing the app never touches the audio.
- **Stages** (`stage.rs`): the trait `Stage` (name, latency in samples, `process` of one `Frame`, `[f32; FRAME_LEN]` in place) runs in the audio path, so no allocations there; `SAMPLE_RATE` (48 kHz) and `FRAME_LEN` (480, 10 ms) are in `lib.rs`. `Chain` (`chain.rs`) runs them in order and sums their latency; `Chain::switches` gives an `Arc<AtomicBool>` per stage to switch it off at runtime: its input delayed by its latency is played instead (the input is always kept for that), and switching crossfades over a frame, so the latency never changes. A switched off stage doesn't process (saves the CPU of DeepFilterNet3, about 2.5 % of a core); switched on again, it resumes from its old state and first runs `Stage::resume_frames` without being played (default its latency in frames; `Denoise` 6: 3 of latency plus 3 the deep filter reaches back), so nothing from before the pause is heard. Warming it up longer was measured and dropped: DeepFilterNet3 takes 1–1.5 s to settle after a pause and keeps differing from a model that ran through for seconds, so the delay wouldn't buy much. Settings the audio path reads are atomics (`atomic::AtomicF32` for floats), e.g. `Denoise::atten_lim`, applied with the next frame. `Denoise` (`denoise.rs`) wraps `DfTract` with preallocated `[1, 480]` arrays, its latency is `DfTract::delay` (30 ms). `HighPass` (`highpass.rs`) removes what's below 80 Hz (4th order Butterworth, two biquads), `Equalizer` (`equalizer.rs`, name `eq`) lowers 250 Hz by 3 dB and raises 3.5 kHz by 3 dB (peaking, Q 1); both are `Biquad`s (`biquad.rs`, Audio EQ Cookbook, transposed direct form II in f64), without latency, but with `resume_frames` for their ringing (4 and 1), parameters fixed until the presets. `DeEsser` (`deesser.rs`, name `deesser`) turns down the band above 5 kHz while its share of the energy is above −7 dB (ratio 4, at most 12 dB, attack 1 ms, release 50 ms), relative, so before the AGC; the band comes from a linear-phase FIR low-pass (97 taps, its delay of 1 ms is the latency), `x + (g − 1) · band` with `band = delayed − low-pass` is the delayed input exactly when it doesn't act (a biquad high-pass for the band shifts its phase, subtracting it took only part of the band away). `Agc` (`agc.rs`, no latency) brings the speech to −18 dBFS RMS: a level smoothed over 0.3 s from frames above the gate (−55 dBFS, so pauses keep the gain), gain within −12…+30 dB, rising 6 dB/s and falling 30 dB/s, ramped within the frame. `Compressor` (`compressor.rs`, no latency, `resume_frames` 3) evens out the loudness within words after the AGC: RMS detector over 5 ms, threshold −24 dBFS, ratio 3:1, soft knee 6 dB, attack 5 ms and release 120 ms on the gain reduction in dB, make-up gain the reduction at 3 dB above the AGC's target (the 5 ms level of speech sits about that much above its long-term one; measured on a recording, the median over 50 ms stays, loud parts −2 dB, quiet ones +2 dB). `Limiter` (`limiter.rs`) keeps the peaks below −1 dBFS with 1 ms lookahead (its latency), attack a quarter of that, release 50 ms, and a clamp as last resort. The chain in `main.rs`: denoise, highpass, eq, deesser, agc, compressor, limiter. `tests/common/mod.rs` measures the gain of a stage at a frequency with a sine.
- **Offline mode** (`offline.rs`): `read_wav` takes 48 kHz only (int or float, channels mixed down to mono), `process` runs the samples frame by frame through the chain, times every stage (mean and max per frame, against the 10 ms a frame may take live) and shifts the output by the chain's latency (padding the input with silence), so it lines up with the input; `write_wav` writes mono 32-bit float. The max times are only meaningful on an idle machine.
- **Live mode** (`live.rs`, `bridge.rs`): two PipeWire streams, `voice-filter-capture` (default microphone, `Stream/Input/Audio`) and `voice-filter` (the virtual microphone, `media.class = Audio/Source`: WirePlumber 0.5.18 never sets a format for `Audio/Source/Virtual`, so it gets no ports), both mono F32 48 kHz, `node.latency = 480/48000`, in one `node.group` (one driver cycle, a virtual source has no clock) and one `node.link-group` (WirePlumber never links the capture stream to our own output). The capture stream is only connected while the output streams (`state_changed`: Streaming connects, Paused disconnects): an inactive but connected capture stream still counts as recording, GNOME would show the microphone as in use. `bridge` connects the callbacks lock-free: `Capture::push` collects the quantum's samples into frames and runs the chain, an `rtrb` ring carries the result, `Playback::pull` hands out exactly `buffer.requested()` samples (not the buffer size, which adds ~250 ms; needs feature `v0_3_49`). No prefill: underruns at the start play silence and let the buffer settle at the latency the quantum and callback order need; more than quantum plus two frames left after a pull gets trimmed to quantum plus one frame (after a pause). The quantum is the graph's, the requested 480 can be lowered by other nodes (256 seen), `tests/bridge.rs` simulates 64…2048 in both and alternating orders. `Stats::bridge_delay` is the exact delay through the bridge at the last pull (from the cycle times of push and pull, the ring level and the samples waiting for a frame; `tests/bridge.rs` checks it against the real one), `capture_delay`/`playback_delay` are what `Stream::time()` reports (delay plus resampler buffer, feature `v0_3_50`). A thread prints frames, max time per frame, silence, dropped samples, errors and the latency (microphone + bridge + chain + app, quantum) every 10 s.
- **Input**: without a target the capture stream gets the default input; if that's "Voice Filter" itself, the link group rules it out and WirePlumber falls back to the source with the highest `priority.session` (here a webcam, 2109, over the USB microphone, 2100). Switching at runtime sets `target.object` with `pw_stream_update_properties` (raw, pipewire-rs has no wrapper) and reconnects a connected capture stream, the chain keeps running. `run --input <node.name>` sets `target.object` and saves the name in `settings.rs` (`$XDG_STATE_HOME/voice-filter/input`, one file per setting), later runs use the saved one; `voice-filter inputs` lists the sources through the registry (sync roundtrip), the saved one marked `*`.
- **Control interface** (`dbus.rs`): `net.b128.VoiceFilter.Daemon` on the session bus, object `/net/b128/VoiceFilter`, interface `net.b128.VoiceFilter1`, served with zbus 6 (no blocking API anymore: a thread of its own sits in `zbus::block_on`, the main thread runs the PipeWire loop). `live::run` starts it before PipeWire; zbus requests names with allow/replace by default, so they're switched off, and a second instance stops with "Voice Filter is already running" instead of taking the name. Settings: property `AttenuationLimit` (0–100 dB, writable, emits changes), method `SetStageEnabled(name, on)`, property `Input` (writable: one of `Inputs` or empty for the default input, saved in the settings), property `Listen` (writable, off at the start); both go as a `dbus::Control` through `Service::send`, a `pipewire::channel` to the PipeWire loop, which owns the streams; status without change signals (clients poll): `Stages`, `Inputs` (`a(ssi)` name, description, priority, kept up to date by a registry listener in `live::watch_inputs`, also used by `voice-filter inputs`), `Latency` (`a{sd}` total and parts in ms), `Quantum`, `MaxFrameTime` (last 10 s, `Stats::last_max_frame_ns` from the report thread), `Counters` (`a{st}`). `tests/dbus.rs` calls the methods directly, without a bus. The name is the reverse of the domain of the commit address; it can still change until the first release.
- **GNOME app** (`voice-filter ui`, module `gui`, behind the default feature `gui`; `--no-default-features` builds without GTK, CI runs clippy that way too): GTK 4 and libadwaita (features up to `v1_4`), app ID `net.b128.VoiceFilter` (a GApplication owns its ID as a bus name, hence the daemon's `.Daemon`). `gui::run` hands GApplication only the program name, the arguments were clap's. The UI is built in code (`gui/window.rs`), no UI files: a combo row for the microphone (the chosen one as its subtitle; an unplugged chosen one stays listed), the switch for listening, switches per stage, a scale for the attenuation limit, status rows; a `StatusPage` while the daemon isn't there. It polls the status every second (`gui/proxy.rs`, zbus proxy with `CacheProperties::No`, the status properties don't emit changes), `updating` keeps the values it shows from being sent back. The proxy's names and types must match `src/dbus.rs`.
- **Listen** (`live::Listen`): while on, a capture stream from `voice-filter` (`target.object`) and a playback stream to the default output, in their own `node.group` and `node.link-group` (`voice-filter-listen`, WirePlumber never links within a link group), with a `bridge` without stages between them; the buffer helpers `read_into`/`write_from` are shared with the main streams. As it records from "Voice Filter" like an app, the filter runs while listening even without an app.
- **Options**: `--atten-lim <dB>` (global, default 100 = unlimited) sets the attenuation limit of DeepFilterNet3 (`Denoise::with_atten_lim`), the default is open until it can be tried in the GNOME app.
- **deep-filter-rt**: DeepFilterNet's `deep_filter` crate (`libDF`, upstream commit `d375b2d`), vendored without its history and reduced to the real-time inference: `lib.rs` (STFT state, ERB features, gains, post filter) and `tract.rs` (`DfParams` loads the model, `DfTract` runs the three ONNX parts encoder, ERB decoder and DF decoder with tract per 10 ms frame). The DeepFilterNet3 model is embedded from the unpacked files in `models/DeepFilterNet3/` (the keys in its `config.ini` belong to the model even where they look like typos, `_typos.toml` excludes the folder). `NOTICE.md` names the origin and lists the changes against upstream (required by Apache-2.0); it's published on its own, so its API is public. Debug builds of tract 0.21 failed on the model with "duplicate name /convt3/Conv.bias" (a debug-only check), 0.23 doesn't.
- The planned architecture (stage trait, 48 kHz frames of 10 ms / 480 samples, fixed 3:1 resampling for Hush (postponed), lock-free settings, D-Bus interface for the GNOME app, offline WAV test mode) is described in `docs/concept.md`. Keep this section in sync with the code once it exists.

## Conventions

- Code, comments and docs are in English.
- CI (`.gitea/workflows/ci.yaml`) runs in the prebuilt image `ci-rust`. Two parallel jobs: `check` (nothing compiles) runs `cargo fmt --all --check`, `cargo deny --locked check`, `cargo machete`, `typos` and `actionlint`/`zizmor` on the workflows, each even if one before failed; `test` runs clippy, `cargo doc` with `RUSTDOCFLAGS=-D warnings`, `cargo +<rust-version> check --locked` (the MSRV, read from `rust-version` in `[workspace.package]` of `Cargo.toml`) and the tests, all with `--workspace`. On pushes to `main`, after both, `release` and then `release-pr` run release-plz (see Releases). `.gitea/workflows/advisories.yaml` runs `cargo deny --locked check advisories` daily. Actions are pinned by commit hash (Renovate updates hash and version comment), checkouts don't persist the token, the workflows only get `contents: read`; the release jobs use the secrets `RELEASE_PLZ_TOKEN` (Gitea token with repository read/write) and `CARGO_REGISTRY_TOKEN`, and bypass the image's registry proxy with an empty `CARGO_HOME`. Once `pipewire-rs` is added, the build needs the PipeWire development files, so the jobs that compile need an image with them.
- Conventional commit prefixes (`chore:`, `docs:`, `build:`, `ci:` …). Dependency upgrades are committed in Renovate's style, also by hand: `chore(deps): …` (e.g. `chore(deps): update dependencies`), release-plz only recognizes that. Only `feat:`, `fix:` and `chore(deps):` end up in the changelog and trigger a release (only if they touch a file of the package), so a user-visible change needs one of them, even if it's part of a refactoring (otherwise as a commit of its own); their description is the changelog entry, written for users.
- Releases are done by release-plz (`release-plz.toml`): the `release-pr` job keeps a PR `chore: bump version (vX.Y.Z)` open that bumps the version in `Cargo.toml`/`Cargo.lock` and adds the `CHANGELOG.md` section, generated from the commits, so there's no hand-written `## Unreleased` section. Merging it makes the `release` job publish to crates.io and create the tag `vX.Y.Z` (unsigned, through the Gitea API) and the Gitea release. `deep-filter-rt` is released the same way with its own version, changelog (`crates/deep-filter-rt/CHANGELOG.md`) and tags `deep-filter-rt-vX.Y.Z`, and gets the semver check, voice-filter doesn't (its library isn't a public API). `release-plz update` shows the bump and changelog locally. **Currently disabled** with `release = false` in `release-plz.toml`, so the skeleton isn't published (the `release` job fails with "no public packages found" meanwhile, that's expected); remove it for the first release.
- `use` statements for external crates (including `std`) start with `::` (e.g. `use ::std::sync::Arc;`); `crate::`/`super::` paths stay as they are. rustfmt has no option for this, so keep it by hand.
- No allocations, locks or syscalls in the audio path (per-frame processing); everything it needs is allocated up front.
