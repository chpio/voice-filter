# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`voice-filter` is going to be a live voice filter for Linux: a single Rust process acting as a PipeWire node that reads the microphone, runs it through a chain of stages (echo cancellation, DeepFilterNet3 denoising, classic DSP voice enhancement; Hush for suppressing other voices is postponed after a test, see the concept) and exposes the result as the virtual microphone "Voice Filter". The design, model choice, latency budget and roadmap are in `docs/concept.md` (started as a German document, now authoritative here). So far there's the vendored DeepFilterNet3 inference (`crates/deep-filter-rt`), the stage chain (echo cancellation with AEC3, DeepFilterNet3, high-pass, EQ, de-esser, AGC, compressor, expander, limiter), the offline mode and a first live mode. Building needs the PipeWire development files, clang (bindgen), GTK 4 and libadwaita (the latter two only for the default feature `gui`).

## Commands

```bash
cargo build
cargo clippy --workspace --all-targets
cargo test --workspace
cargo test --release -p deep-filter-rt   # the model runs about 10x faster than in debug builds
cargo run --release -- process in.wav out.wav   # offline mode, prints latency and time per stage
cargo run --release -- process in.wav out.wav --reference played.wav   # with what the speakers played, for the echo cancellation
cargo run --release -- run [--input <name>] [--output <name>]   # live: the virtual microphone "Voice Filter", until Ctrl+C
cargo run --release -- inputs                   # the microphones for --input
cargo run --release -- outputs                  # the output devices for --output (the echo of which gets removed)
cargo run -- ui                                 # the GNOME app, needs `run` for its controls
cargo run -- install-desktop                    # its desktop entry and icon into ~/.local/share
cargo fmt --all            # 4 spaces (rustfmt default, matches .editorconfig)
cargo deny check           # licenses, advisories, sources (deny.toml)
cargo machete              # unused dependencies
typos                      # spell check
```

Tests live in `tests/` of each crate (integration tests against the library, no inline `#[cfg(test)]` modules).

## Architecture

- **Workspace**: the root package `voice-filter` and `crates/deep-filter-rt`; edition, MSRV and license are shared in `[workspace.package]` of the root `Cargo.toml`.
- **Crate layout** of voice-filter: all modules live in the library (`lib.rs`) so tests under `tests/` can use them; the binary (`main.rs`, clap, subcommands `run`, `inputs`, `outputs`, `process`, `ui`) only wires them up. One binary, but the daemon (`run`) and the app (`ui`) are separate processes, so closing or crashing the app never touches the audio.
- **Stages** (`stage.rs`): the trait `Stage` (name, latency in samples, `process` of one `Frame`, `[f32; FRAME_LEN]` in place) runs in the audio path, so no allocations there; `SAMPLE_RATE` (48 kHz) and `FRAME_LEN` (480, 10 ms) are in `lib.rs`. `Chain` (`chain.rs`) runs them in order and sums their latency; `Chain::switches` gives an `Arc<AtomicBool>` per stage to switch it off at runtime: its input delayed by its latency is played instead (the input is always kept for that), and switching crossfades over a frame, so the latency never changes. A switched off stage doesn't process (saves the CPU of DeepFilterNet3, about 2.5 % of a core); switched on again, it resumes from its old state and first runs `Stage::resume_frames` without being played (default its latency in frames; `Denoise` 6: 3 of latency plus 3 the deep filter reaches back), so nothing from before the pause is heard. Warming it up longer was measured and dropped: DeepFilterNet3 takes 1–1.5 s to settle after a pause and keeps differing from a model that ran through for seconds, so the delay wouldn't buy much. Settings the audio path reads are atomics (`atomic::AtomicF32` for floats), the parameters of the stages are `Param`s (see Parameters), applied with the next frame. `Denoise` (`denoise.rs`) wraps `DfTract` with preallocated `[1, 480]` arrays, its latency is `DfTract::delay` (30 ms). `HighPass` (`highpass.rs`) removes what's below 80 Hz (4th order Butterworth, two biquads), `Equalizer` (`equalizer.rs`, name `eq`) lowers 250 Hz by 3 dB and raises 3.5 kHz by 3 dB (peaking, Q 1); both are `Biquad`s (`biquad.rs`, Audio EQ Cookbook, transposed direct form II in f64), without latency, but with `resume_frames` for their ringing (the high-pass from its frequency, 4 at 80 Hz; the EQ 1); defaults as above, adjustable (see Parameters). `DeEsser` (`deesser.rs`, name `deesser`) turns down the band above 5 kHz while its share of the energy is above −7 dB (ratio 4, at most 12 dB, attack 1 ms, release 50 ms), relative, so before the AGC; the band comes from a linear-phase FIR low-pass (97 taps, its delay of 1 ms is the latency), `x + (g − 1) · band` with `band = delayed − low-pass` is the delayed input exactly when it doesn't act (a biquad high-pass for the band shifts its phase, subtracting it took only part of the band away). `Agc` (`agc.rs`, no latency) brings the speech to −18 dBFS RMS: a level smoothed over 0.3 s from frames above the gate (−55 dBFS, so pauses keep the gain) and 10 dB above the noise floor (`level::NoiseFloor`, the quietest frame of the last 2 s, blocks of 100 ms, so steady noise like mains hum keeps the gain too: with the gate alone, hum at −50 dBFS was raised to −18 dBFS within 4 s of silence; speech dips to the floor between syllables, the AGC's tests use syllables of 300 ms with 100 ms of silence, a steady tone counts as noise), in runs of at least 8 such frames (80 ms: a syllable is longer, a keystroke 10–50 ms; on a live recording with a noisy built-in microphone, typing in a pause raised the gain from 7 to 30 dB within 20 s, and with it the hiss and hum the noise suppression left, from −50 to −22 dBFS) and, with `Agc::listening` (as the expander, the estimate held back by `ahead` frames, the latency of denoise, at most `MAX_AHEAD`, so it belongs to the frame), where DeepFilterNet3's local SNR is above `threshold` (0 dB; −20 dB, `SNR_OFF_DB`, below its lowest estimate, turns it off, as does denoise switched off); in for testing live: on two recordings the estimate dropped below 0 dB within words too (143 of the 160 frames it left out of a live recording, some at −13 dBFS), lowering the gain by 1 dB on average and up to 9 dB, while only 17 frames in 89 s it left out weren't next to speech, gain within −12…+30 dB, rising 6 dB/s and falling 30 dB/s, ramped within the frame. `Compressor` (`compressor.rs`, no latency, `resume_frames` 3) evens out the loudness within words after the AGC: RMS detector over 5 ms, threshold −24 dBFS, ratio 3:1, soft knee 6 dB, attack 5 ms and release 120 ms on the gain reduction in dB, make-up gain the reduction at 3 dB above the AGC's target (the 5 ms level of speech sits about that much above its long-term one; measured on a recording, the median over 50 ms stays, loud parts −2 dB, quiet ones +2 dB). `Limiter` (`limiter.rs`) keeps the peaks below −1 dBFS (by default) with 1 ms lookahead (its latency), attack a quarter of that, release 50 ms (by default), and a clamp as last resort. The chain in `main.rs`: echo, denoise, highpass, eq, deesser, agc, compressor, expander, limiter. `Expander` (`expander.rs`, no latency) keeps the noise down in speech pauses (what the AGC and the make-up gain raise): it turns down by `range` (20 dB) unless it hears speech, holds open `hold` (200 ms) after it and closes over 150 ms (linear in dB), opens within a frame. It opens for a level above `level` (−50 dBFS; the pauses lie at −55 to −65 dBFS after the compressor) or for DeepFilterNet3's local SNR above `threshold` (0 dB, catches quieter speech); with the SNR alone it cut up to 20 % of the quieter speech and word ends on the recordings (heard live), with the level too none on two and 1.7 % on a very quiet one: `Denoise::speech` shares a `denoise::Speech` (the SNR of the newest analyzed frame and a frame counter, updated from `DfTract::process`'s return value), `Expander::listening` takes it; the estimate is 30 ms ahead of the audio it belongs to, so the expander opens before a word. While the counter doesn't move (denoise switched off) only the level counts. Short pauses between sentences go 10–20 dB down (single louder noise frames open it for the hold time). `tests/common/mod.rs` measures the gain of a stage at a frequency with a sine.
- **Offline mode** (`offline.rs`): `read_wav` takes 48 kHz only (int or float, channels mixed down to mono), `process` runs the samples frame by frame through the chain, times every stage (mean and max per frame, against the 10 ms a frame may take live) and shifts the output by the chain's latency (padding the input with silence), so it lines up with the input; with a reference (`--reference`, what the speakers played) it pushes its frame into the echo canceller's `Reference` before each frame, as live; `write_wav` writes mono 32-bit float. The max times are only meaningful on an idle machine.
- **Live mode** (`live.rs`, `bridge.rs`): three PipeWire streams, `voice-filter-capture` (default microphone, `Stream/Input/Audio`), `voice-filter-reference` (the monitor of an output device, `stream.capture.sink = true`, the reference of the echo canceller) and `voice-filter` (the virtual microphone, `media.class = Audio/Source`: WirePlumber 0.5.18 never sets a format for `Audio/Source/Virtual`, so it gets no ports), all mono F32 48 kHz (PipeWire mixes a stereo monitor down), `node.latency = 480/48000`; capture and virtual microphone in one `node.group` (one driver cycle, a virtual source has no clock) and one `node.link-group` (WirePlumber never links the capture stream to our own output). The reference stream is deliberately in neither: PipeWire puts the nodes of a group and of a link group on one driver, so the output device ran under the USB microphone's clock and its quantum of 256 while an app recorded, with xruns at every join and leave (511 at the output, 3134 at Firefox's playback, which wants 900–3600, seen in `pw-top`, heard as dropouts and choppy video). On its own it follows the output device's clock and hands over through the `Reference` ring; `stream.capture.sink` keeps it on output devices. The capture streams are only connected while something records from `voice-filter` (`capture_while_recorded`: registry listener on the links from its node, the first connects, the last gone disconnects): an inactive but connected capture stream still counts as recording, GNOME would show the microphone as in use. Not the output stream's state: in a group with the capture stream, which the microphone drives, the node stays running after the last app left, so it never paused again. GNOME Settings' level meter ("Peak detect", `stream.monitor = true`, not in the registry's node properties) counts as recording too while the sound panel is open. `bridge` connects the callbacks lock-free: `Capture::push` collects the quantum's samples into frames and runs the chain, an `rtrb` ring carries the result, `Playback::pull` hands out exactly `buffer.requested()` samples (not the buffer size, which adds ~250 ms; needs feature `v0_3_49`). No prefill: underruns at the start play silence and let the buffer settle at the latency the quantum and callback order need; more than quantum plus two frames left after a pull gets trimmed to quantum plus one frame (after a pause). The quantum is the graph's, the requested 480 can be lowered by other nodes (256 seen), `tests/bridge.rs` simulates 64…2048 in both and alternating orders. `Capture` also measures the levels (`level.rs`): `Stats::input_db`/`output_db` before and after the chain as a `level::Meter` (RMS per frame, falling 20 dB/s) and `input_floor_db`, the `NoiseFloor` of the microphone. `Stats::bridge_delay` is the exact delay through the bridge at the last pull (from the cycle times of push and pull, the ring level and the samples waiting for a frame; `tests/bridge.rs` checks it against the real one), `capture_delay`/`playback_delay` are what `Stream::time()` reports (delay plus resampler buffer, feature `v0_3_50`). A thread prints frames, max time per frame, silence, dropped samples, errors and the latency (microphone + bridge + chain + app, quantum) every 10 s.
- **Echo cancellation** (`echo.rs`, stage `echo`, first in the chain): AEC3 from sonora (pure Rust port of WebRTC's audio processing), only its echo canceller on (no noise suppression, no AGC2), internal rate set to 48 kHz (its default 32 kHz would cut above 16 kHz). `Echo::new` gives the stage and a `Reference`, the producer of an `rtrb` ring (16384 samples) the reference stream pushes into from its callback (what doesn't fit gets dropped); `process` first feeds every whole frame of the reference to `process_render_f32` (AEC3 buffers it and estimates its delay to the microphone), then the frame to `process_capture_f32`. Latency 238 samples (5 ms, its 4 ms blocks and the three-band split of 48 kHz; measured with noise, `tests/echo.rs`), `resume_frames` the ring's length. `EchoStatus` (shared by the stage and its `Reference`, atomics updated every frame): frame counters of the microphone and of the reference (they stop while it's off or no app records, or while the speakers are idle), the peak level of the reference (falling 60 dB/s) and AEC3's ERLE, ERL and delay from `AudioProcessing::statistics()` (no allocation; ERLE/ERL only of its linear filter, the delay in steps of 4 ms, 0 with the USB microphone here); D-Bus `Echo`, the app's status row under the speakers. FTZ/DAZ are set in the MXCSR around the calls (`FlushDenormals`, x86_64, inline `stmxcsr`/`ldmxcsr`) as WebRTC does: denormals while the reference is silent make AEC3 10–50× slower (sonora issue #34). sonora 0.2.0 allocates ~40 times per frame, so the workspace patches all sonora crates to the commit of its PR #40 (`[patch.crates-io]` in `Cargo.toml`, the git source allowed in `deny.toml`; a published crate falls back to 0.2.0); `tests/echo.rs` counts the allocations per frame with a thread-local counting allocator (0 with the patch, 21750 in 500 frames without). Remove the patch with sonora's next release. Spike, test recordings and alternatives in the concept.
- **Devices**: without a target the capture stream gets the default input; if that's "Voice Filter" itself, the link group rules it out and WirePlumber falls back to the source with the highest `priority.session` (here a webcam, 2109, over the USB microphone, 2100). Switching at runtime sets `target.object` with `pw_stream_update_properties` (raw, pipewire-rs has no wrapper) and reconnects a connected capture stream, the chain keeps running. `run --input <node.name>` sets `target.object` and saves the name in `settings.rs` (`$XDG_STATE_HOME/voice-filter/input`, one file per device, see Saved settings), later runs use the saved one; `voice-filter inputs` lists the sources through the registry (sync roundtrip), the saved one marked `*`. The output device for the reference works the same (`run --output`, `$XDG_STATE_HOME/voice-filter/output`, `voice-filter outputs` lists the sinks, `live::Devices`, `live::devices(Direction)`), without a target the default output; switching sets the reference stream's `target.object`.
- **Control interface** (`dbus.rs`): `net.b128.VoiceFilter.Daemon` on the session bus, object `/net/b128/VoiceFilter`, interface `net.b128.VoiceFilter1`, served with zbus 6 (no blocking API anymore: a thread of its own sits in `zbus::block_on`, the main thread runs the PipeWire loop). `live::run` starts it before PipeWire; zbus requests names with allow/replace by default, so they're switched off, and a second instance stops with "Voice Filter is already running" instead of taking the name. Settings: method `SetStageEnabled(name, on)`, property `Parameters` (`a(ssssddddd)` stage, name, title, unit, min, max, step, default, value; no change signals) with method `SetParameter(stage, name, value)` (outside the range `InvalidArgs`); both methods save the stages and parameters (`settings::save_chain`), property `Input` (writable: one of `Inputs` or empty for the default input, saved in the settings), property `Output` (the same for the output device of the reference, one of `Outputs`), property `Listen` (writable, off at the start unless kept), `KeepListen` (writable, saved: whether `Listen` is kept for the next runs, off by default since the microphone stays in use while listening) and `ListenVolume` (writable, dB, −40…0, saved); they go as a `dbus::Control` through `Service::send`, a `pipewire::channel` to the PipeWire loop, which owns the streams; status without change signals (clients poll): `Stages`, `Inputs` and `Outputs` (`a(ssi)` name, description, priority, kept up to date by registry listeners in `live::watch_devices`, also used by `voice-filter inputs`/`outputs`), `Latency` (`a{sd}` total and parts in ms), `Echo` (`a{sd}`, see `EchoStatus`; empty without echo stage), `Quantum`, `MaxFrameTime` (last 10 s, `Stats::last_max_frame_ns` from the report thread), `Levels` (`a{sd}` `input`, `output`, `input-floor` in dBFS), `Counters` (`a{st}`). `tests/dbus.rs` calls the methods directly, without a bus. The name is the reverse of the domain of the commit address; it can still change until the first release.
- **GNOME app** (`voice-filter ui`, module `gui`, behind the default feature `gui`; `--no-default-features` builds without GTK, CI runs clippy that way too): GTK 4 and libadwaita (features up to `v1_4`), app ID `net.b128.VoiceFilter` (a GApplication owns its ID as a bus name, hence the daemon's `.Daemon`). `gui::run` hands GApplication only the program name, the arguments were clap's. Desktop entry and icon (SVG, a microphone on a blue tile between a noisy and a clean wave) are in `data/` (named after the app ID, in the published crate via `include`), embedded by `gui/desktop.rs`: `install-desktop` writes them into `$XDG_DATA_HOME` with `Exec` set to the full path of the running binary (quoted per the desktop entry spec, with the backslashes of the quoting escaped again as in every value; GLib rejects the entry otherwise, `tests/desktop.rs` reads it back with GLib) and updates the hicolor icon cache if a tool for it is there (`~/.local/share/icons/hicolor` had a cache here, a stale one hides new icons); GNOME Shell takes a window's icon only from the desktop entry of its app ID, `set_default_icon_name` covers other desktops. The UI is built in code (`gui/window.rs`), no UI files: a combo row for the microphone (the chosen one as its subtitle; an unplugged chosen one stays listed), the switch for listening, a row per stage, built from `Parameters` with the first status (and again when its stages or parameters change): with parameters an `ExpanderRow` whose enable switch switches the stage and that expands to a scale per parameter (the default marked), without a `SwitchRow`; the row of `echo` is an `ExpanderRow` anyway and holds the combo row of the output device ("Speakers") and a status row (`show_echo`: not running if the capture counter didn't move since the last poll, silent speakers if the reference counter didn't or its level is below −60 dBFS, else the level of the speakers and the delay; not AEC3's ERLE/ERL, which only cover its linear filter: a recording it reported 5–7 dB ERLE and ERL stuck at 20 dB for lost 30 dB of echo), both moved over when the rows are rebuilt; microphone and output device share `Device`, `connect_device` and `show_devices`; the groups (`GROUPS`) and titles (`STAGES`) are in the window, a group with meters of the microphone and the output (`gtk::LevelBar` without its offsets, −60…0 dBFS, `Levels` read every 100 ms while the frame counter moved at the last status poll) and the noise floor as the subtitle of the microphone's, with a hint above −45 dBFS for 5 polls in a row (the built-in microphone here sat at −27 dBFS and the noise suppression left a hiss), status rows (dropouts shown in ms); every expanding stage row ends with a row that resets its parameters (`SetParameter` with each default, the button only sensitive while one differs), the main menu of the header bar has "Reset the Filter…" (`win.reset`, an `adw::MessageDialog` asks first; all stages on, all parameters to their defaults, not the devices); every stage, parameter and status row has an info button (`gui/help.rs`, a flat `MenuButton` with a popover) with what it does, the texts by stage and parameter name, so a new parameter needs one there; a `StatusPage` while the daemon isn't there. It polls the status every second (`gui/proxy.rs`, zbus proxy with `CacheProperties::No`, the status properties don't emit changes), `updating` keeps the values it shows from being sent back. The proxy's names and types must match `src/dbus.rs`.
- **Listen** (`live::Listen`): while on, a capture stream from `voice-filter` (`target.object`) and a playback stream to the default output, in their own `node.group` and `node.link-group` (`voice-filter-listen`, WirePlumber never links within a link group), with a `bridge` between them whose only stage is a `volume::Volume` (its `Param` is created once in `live::run` and shared by every start, so the volume survives switching Listen off and on; the app's slider takes its range from `volume::param()`), and `node.dont-fallback` on the capture stream (without "Voice Filter", e.g. when Listen starts with the daemon, WirePlumber would otherwise link the default source and play the unfiltered microphone); the buffer helpers `read_into`/`write_from` are shared with the main streams. As it records from "Voice Filter" like an app, the filter runs while listening even without an app.
- **Parameters** (`param.rs`): `Param` (name, title, unit, min, max, step, default, the value as a shared `AtomicF32`; `set` refuses values outside the range) is a setting a stage reads at the start of every frame; `Stage::params` hands them out once, `Chain::params` collects them with the stage name for the control interface. Changed filters recompute their coefficients in the audio path (`Biquad::retune` keeps the state, so it doesn't click; the de-esser recomputes its 97 taps). They are: denoise `limit`, highpass `freq`, eq `low-mid`/`presence`/`presence-freq`, deesser `threshold`/`freq`, agc `target`/`max-gain`/`threshold`, compressor `threshold`/`ratio` (its make-up gain follows the AGC's `target`, `Compressor::following`), expander `range`/`threshold`/`hold`/`level`, limiter `ceiling`/`release` (not its lookahead, that's its latency). Every stage has some, so every row in the app expands the same way (a `SwitchRow` among `ExpanderRow`s sits its switch elsewhere).
- **Saved settings** (`settings.rs`, `$XDG_STATE_HOME/voice-filter/`): `input` and `output` (see Devices), `listen-volume`, `listen` (only while `KeepListen` is on: `on`/`off`, the file's existence is the `KeepListen`; `live::run` starts Listen with the main streams if it says `on`) and `chain`, the stages switched off (`denoise off`) and the parameters not at their default (`denoise.limit 30`), one per line, so a default changed in the code applies to what the user never touched. `save_chain` rewrites it from the switches and params on every `SetStageEnabled`/`SetParameter` (all files go through a temporary file and a rename, a dragged slider saves many times); `run` applies it with `restore_chain` before it starts, lines that don't fit (unknown stage or parameter, out of range, unreadable) are skipped with a warning each. The offline mode doesn't read it, its runs stay comparable.
- **Options**: `--atten-lim <dB>` (global, 100 and above = unlimited) sets the attenuation limit of DeepFilterNet3 (`Denoise::with_atten_lim`); `run` applies it over the saved settings and saves it, `process` without it takes the default (unlimited); the default is open until it can be tried in the GNOME app.
- **deep-filter-rt**: DeepFilterNet's `deep_filter` crate (`libDF`, upstream commit `d375b2d`), vendored without its history and reduced to the real-time inference: `lib.rs` (STFT state, ERB features, gains, post filter) and `tract.rs` (`DfParams` loads the model, `DfTract` runs the three ONNX parts encoder, ERB decoder and DF decoder with tract per 10 ms frame). The DeepFilterNet3 model is embedded from the unpacked files in `models/DeepFilterNet3/` (the keys in its `config.ini` belong to the model even where they look like typos, `_typos.toml` excludes the folder). `NOTICE.md` names the origin and lists the changes against upstream (required by Apache-2.0); it's published on its own, so its API is public. Debug builds of tract 0.21 failed on the model with "duplicate name /convt3/Conv.bias" (a debug-only check), 0.23 doesn't.
- The design behind it (stage trait, 48 kHz frames of 10 ms / 480 samples, fixed 3:1 resampling for Hush (postponed), lock-free settings, D-Bus interface for the GNOME app, offline WAV test mode) is described in `docs/concept.md`. Keep this section in sync with the code, and with it the user docs: `README.md` (features, stage table, usage, D-Bus table) and the status, stage table and roadmap in `docs/concept.md`.

## Conventions

- Code, comments and docs are in English.
- CI (`.gitea/workflows/ci.yaml`) runs in the prebuilt image `ci-rust`. Two parallel jobs: `check` (nothing compiles) runs `cargo fmt --all --check`, `cargo deny --locked check`, `cargo machete`, `typos` and `actionlint`/`zizmor` on the workflows, each even if one before failed; `test` runs clippy, `cargo doc` with `RUSTDOCFLAGS=-D warnings`, `cargo +<rust-version> check --locked` (the MSRV, read from `rust-version` in `[workspace.package]` of `Cargo.toml`) and the tests, all with `--workspace`. On pushes to `main`, after both, `release` and then `release-pr` run release-plz (see Releases). `.gitea/workflows/advisories.yaml` runs `cargo deny --locked check advisories` daily. Actions are pinned by commit hash (Renovate updates hash and version comment), checkouts don't persist the token, the workflows only get `contents: read`; the release jobs use the secrets `RELEASE_PLZ_TOKEN` (Gitea token with repository read/write) and `CARGO_REGISTRY_TOKEN`, and bypass the image's registry proxy with an empty `CARGO_HOME`. Once `pipewire-rs` is added, the build needs the PipeWire development files, so the jobs that compile need an image with them.
- Conventional commit prefixes (`chore:`, `docs:`, `build:`, `ci:` …). Dependency upgrades are committed in Renovate's style, also by hand: `chore(deps): …` (e.g. `chore(deps): update dependencies`), release-plz only recognizes that. Only `feat:`, `fix:` and `chore(deps):` end up in the changelog and trigger a release (only if they touch a file of the package), so a user-visible change needs one of them, even if it's part of a refactoring (otherwise as a commit of its own); their description is the changelog entry, written for users.
- Releases are done by release-plz (`release-plz.toml`): the `release-pr` job keeps a PR `chore: bump version (vX.Y.Z)` open that bumps the version in `Cargo.toml`/`Cargo.lock` and adds the `CHANGELOG.md` section, generated from the commits, so there's no hand-written `## Unreleased` section. Merging it makes the `release` job publish to crates.io and create the tag `vX.Y.Z` (unsigned, through the Gitea API) and the Gitea release. `deep-filter-rt` is released the same way with its own version, changelog (`crates/deep-filter-rt/CHANGELOG.md`) and tags `deep-filter-rt-vX.Y.Z`, and gets the semver check, voice-filter doesn't (its library isn't a public API). `release-plz update` shows the bump and changelog locally. **Currently disabled** with `release = false` in `release-plz.toml`, so the skeleton isn't published (the `release` job fails with "no public packages found" meanwhile, that's expected); remove it for the first release.
- `use` statements for external crates (including `std`) start with `::` (e.g. `use ::std::sync::Arc;`); `crate::`/`super::` paths stay as they are. rustfmt has no option for this, so keep it by hand.
- No allocations, locks or syscalls in the audio path (per-frame processing); everything it needs is allocated up front.
